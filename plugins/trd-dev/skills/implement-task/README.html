implement-task

How the skill turns defined tasks into built, tested, and independently verified code.

implement-task takes one or more implementation tasks — from ticket ids or numbered tasks in an HTML implementation plan, given individually (10, 12, 15) or as an inclusive range (10..15 or 10...15 → every id from 10 to 15) — and builds each one with disciplined engineering: test-driven development, KISS/YAGNI, and then an independent verification stage before moving on. When no formal requirement exists, it works straight from the ticket or the description you provide.

Top-level flow

Tasks are implemented one at a time, in order — they share a working tree and build on each other, so they never run in parallel. Each task runs through a build stage, then a verification stage, then a fix loop until its verdict is clean.

The loop is strictly sequential: task N+1 does not start until task N's verdict is clean or the user is brought in.

Inside the build stage One agent

Building is inherently serial: each TDD cycle depends on the last, and it all shares one working tree. A single agent carries the whole stage.

Inside the verification stage One read-only agent

The build agent just wrote the code, so it is the wrong reviewer for its own work — anchored on its own mental model and blind to its own scope creep. Verification brings in fresh eyes. The passing tests already prove the task does what its acceptance criteria ask, so verification does not re-walk conformance. It covers the two things tests miss, both handled by a single independent read-only agent: 

flowchart TD
    In([Task built, tests green]) --> U["Check 1 — Unrequested / dangerous behavior
scan the diff for behavior
never asked for; rate severity"]
    U --> S["Check 2 — Side effects
predict other affected areas,
then read that code and confirm/refute"]
    S --> Merge[Drop refuted findings,
keep only file:line-cited problems]
    Merge --> V([Verdict: clean / fixable / fundamental])

    classDef seq fill:#eef4ff,stroke:#2d6cdf,color:#1a1a1a;
    class U,S,Merge seq;
CheckLooks for
Unrequested / dangerous behavior Scope creep, silent side effects, weakened validation or permissions, data loss, broadened attack surface, debug/backdoor code, changed defaults, swallowed errors. Ignores behavior the requirement explicitly authorizes.
Side effects Predicts other modules, callers, shared state, contracts, or UX flows the change could affect, then actually reads that code and decides whether the change breaks, contradicts, or is inconsistent with it — confirming or refuting each with a file:line citation.

How the pieces run together

    participant O as Orchestrator
    participant B as Build agent
    participant V as Verifier

    Note over O: Tasks run one at a time, in order
    O->>B: Implement task N (spec + requirement)
    activate B
    B-->>O: Built, tests green
    deactivate B

    O->>V: Review diff (unrequested behavior + side effects)
    activate V
    V-->>O: Findings, confirmed / refuted (file:line)
    deactivate V

    alt Fixable problems
        O->>B: Fix confirmed issues (TDD)
        B-->>O: Fixed
        O->>V: Re-verify
    else Clean
        Note over O: Move to task N+1
    end
