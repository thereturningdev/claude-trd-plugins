implement-task

How the skill turns defined tasks into built, tested, and independently verified code.

implement-task takes one or more implementation tasks — from ticket ids or numbered tasks in an HTML implementation plan, given individually (10, 12, 15) or as an inclusive range (10..15 or 10...15 → every id from 10 to 15) — and builds each one with disciplined engineering: test-driven development, KISS/YAGNI, an adversarial edge-case pass, and then an independent verification stage before moving on. When no formal requirement exists, it works straight from the ticket or the description you provide.

Sequential (one agent, in order) Parallel (independent agents at once)

Top-level flow

Tasks are implemented one at a time, in order — they share a working tree and build on each other, so they never run in parallel. Each task runs through a build stage, then a verification stage, then a fix loop until its verdict is clean.

The loop is strictly sequential: task N+1 does not start until task N's verdict is clean or the user is brought in.

Inside the build stage Sequential — 1 agent

Building is inherently serial: each TDD cycle depends on the last, and it all shares one working tree. A single agent carries the whole stage.

Inside the verification stage Parallel — 2 agents

The build agent just wrote the code, so it is the wrong reviewer for its own work — anchored on its own mental model and blind to its own scope creep. Verification brings in fresh, adversarial eyes. The passing tests and adversarial pass already prove the task does what its acceptance criteria ask, so verification does not re-walk conformance. It covers the two things tests miss, in two independent read-only agents that run at the same time: 

flowchart TD
    In([Task built, tests green]) --> Fork(( ))

    Fork --> U["Agent 1 — Unrequested / dangerous behavior
scan the diff for behavior
never asked for; rate severity"]
    Fork --> S["Agent 2 — Side effects
predict other affected areas,
then read that code and confirm/refute"]

    U --> Join(( ))
    S --> Join
    Join --> Merge[Merge findings, drop refuted,
keep only file:line-cited problems]
    Merge --> V([Verdict: clean / fixable / fundamental])

    classDef par fill:#fff4e8,stroke:#b5670a,color:#1a1a1a;
    classDef seq fill:#eef4ff,stroke:#2d6cdf,color:#1a1a1a;
    class U,S par;
    class Merge seq;
AgentLooks for
Unrequested / dangerous behavior Scope creep, silent side effects, weakened validation or permissions, data loss, broadened attack surface, debug/backdoor code, changed defaults, swallowed errors. Ignores behavior the requirement explicitly authorizes.
Side effects Predicts other modules, callers, shared state, contracts, or UX flows the change could affect, then actually reads that code and decides whether the change breaks, contradicts, or is inconsistent with it — confirming or refuting each with a file:line citation.

Where sequential vs. parallel matters

PartModeWhy
Task listSequentialTasks share a working tree and build on each other.
Build stageSequentialEach TDD cycle depends on the previous one.
VerificationParallelThe two reviews are independent, so run at once for speed.
Fix loopSequentialThe build agent fixes, then re-verification runs.
